# Cold-Start-Aware Electronics Recommendation System

**Status:** Proposed design — documentation phase only
**Project level:** Third-year college semester project
**Time budget:** 10 days, approximately 1 hour per day
**Last updated:** 2026-11-10

## 1. Intent

Build a small, explainable e-commerce recommendation prototype for electronics products. The project will demonstrate why a conventional recommender tends to favor established brands and how a cold-start-aware approach can give suitable exposure to a genuinely useful product from a new brand.

The project is not intended to reproduce Amazon or operate as a production marketplace. It is an educational demonstration of machine learning concepts, recommendation methods, and the new-item/new-user cold-start problem.

## 2. Problem statement

A new electronics brand may offer a television, laptop, phone, or similar product with a competitive price, better specifications, a stronger warranty, or a valuable offer. However, it has little or no click, purchase, rating, or review history. A recommender that depends mainly on past interactions or popularity may continue recommending older, familiar brands.

This creates a feedback loop:

1. The new product receives little exposure.
2. It collects few interactions.
3. The recommender interprets the lack of interactions as weak evidence.
4. The product continues to be hidden from suitable users.

The system will make this behavior visible and compare it with a hybrid cold-start strategy that uses product information and limited user preferences.

## 3. Goals

- Create a clearly documented electronics dataset for the experiment.
- Demonstrate both new-item and new-user cold-start scenarios.
- Implement a popularity/rating baseline recommender.
- Implement a content-based or hybrid cold-start-aware recommender.
- Use product features such as category, price, discount, specifications, warranty, rating, brand age, and value score.
- Demonstrate classification and clustering as required learning components.
- Compare methods using understandable recommendation metrics.
- Provide a small Streamlit web demo that a student can explain during a review or viva.
- Produce a Word-compatible report, presentation, charts, source code, and a learning guide.
- Keep components modular so the dataset or model can be replaced later.

## 4. Non-goals

- Production-scale deployment, authentication, payments, or order processing.
- Scraping Amazon or using private customer data.
- Claiming that synthetic data represents real customer behavior.
- Building a high-accuracy commercial recommender.
- Requiring deep learning for the core working system.
- Recreating Amazon's branding, interface, or proprietary algorithms.

## 5. Anti-goals and failure conditions

The project should not be considered successful if:

- the demo only displays hard-coded recommendations without a model or documented logic;
- synthetic records are presented as real customer data;
- the new-brand scenario cannot be reproduced;
- the system recommends products without showing a reason;
- deep learning makes the project too difficult to complete or explain;
- the report includes metrics without explaining the evaluation setup and limitations.

## 6. Intended users and demo scenario

The primary user is a shopper selecting an electronics category and preferences such as budget, desired features, minimum warranty, and interest in value-for-money products.

The demo should support a repeatable scenario:

1. Select a category such as television.
2. Select or enter a budget and preferences.
3. View baseline recommendations dominated by established brands.
4. View cold-start-aware recommendations.
5. Inspect why a new-brand item was included, such as price, discount, specifications, warranty, and feature similarity.
6. Compare simple metrics or a chart showing exposure/coverage differences.

The interface may also provide a new-user mode in which the user supplies a few preferences instead of a long history.

## 7. Data strategy

No dataset has been supplied. The initial project will use a documented synthetic electronics dataset generated by a reproducible script. This is an explicit project call because a small public dataset is unlikely to contain all of the required fields and controlled cold-start cases.

The generated data should contain separate logical entities:

- `products`: product ID, category, brand, brand age, product age, price, discount, rating, review count, warranty years, key specifications, value score, and whether the item is a new-brand/new-item case;
- `users`: user ID, preferred categories, budget range, preferred feature values, and an optional new-user flag;
- `interactions`: user ID, product ID, event type, timestamp or ordering field, and an interaction strength/label;
- optional `offers`: discount or promotion fields if they are not kept in `products`.

The generator must use a fixed seed and document how many products, users, and interactions it creates. It should intentionally include products with zero historical interactions so the cold-start evaluation is possible.

If a public dataset is later adopted, it must be cited and the synthetic augmentation must remain clearly separated in the report.

## 8. Machine-learning approach

### 8.1 Required learning demonstrations

The project will explain:

- supervised versus unsupervised learning;
- classification using a small comparison of Logistic Regression, Decision Tree, Random Forest, and K-Nearest Neighbors where feasible;
- clustering using K-Means for user or product groups;
- train/test splitting, feature scaling, feature engineering, and evaluation metrics.

The classification target may be a synthetic or interaction-derived label such as whether a user is likely to engage with a product. The target definition and limitations must be documented so it is not confused with actual purchasing intent.

### 8.2 Recommendation baseline

Implement a simple popularity/rating baseline that ranks products using historical interaction count, rating, review count, or a clearly documented combined score. The baseline should naturally favor established items and make the cold-start limitation visible.

### 8.3 Proposed cold-start recommender

Implement an explainable content-based or hybrid strategy:

1. Encode product categorical and numeric attributes.
2. Encode a user's selected preferences or known interaction profile.
3. Calculate product-user similarity using cosine similarity or a comparable documented method.
4. Add a controlled value/quality component using normalized specifications, warranty, discount, and price fit.
5. Apply a small, transparent cold-start exposure adjustment for suitable new products rather than blindly promoting every new product.
6. Return top-K recommendations with human-readable reasons.

Collaborative filtering may be included as an optional comparison if the time budget allows, but it must not block the content-based solution.

### 8.4 Deep-learning boundary

Deep learning is optional enhancement, not a dependency for the main solution. If time remains, implement a small multilayer perceptron classifier with scikit-learn or a minimal neural-network comparison and explain why it is not automatically superior on a small synthetic dataset. Do not introduce a complex neural recommender, embeddings pipeline, or external training service in the initial scope.

## 9. Evaluation

Use a reproducible holdout or simulated-time split and state the split method in the report. Evaluation should include:

- classification: accuracy, precision, recall, F1-score, and confusion matrix;
- clustering: silhouette score and a plain-language interpretation of clusters;
- recommendations: Precision@K and Recall@K if suitable positive interactions are available;
- cold-start-specific outcomes: new-item exposure rate, catalog coverage, and the proportion of relevant new-brand items appearing in top-K results;
- quality safeguards: average rating/value score and a check that exposure adjustment does not overwhelm relevance.

The report must distinguish offline experiment results from an interactive demo. Results on synthetic data must be described as illustrative, not evidence of real-world commercial performance.

## 10. Application and deliverables

The project directory should eventually contain:

- reproducible data-generation and preprocessing code;
- model/recommender modules;
- Streamlit application;
- tests or smoke checks for core behavior;
- saved experiment results and charts;
- `README.md` with setup and run instructions;
- Word-compatible report source, preferably Markdown plus a conversion script or `.docx` generation script;
- PowerPoint outline/source and the final presentation file if tooling permits;
- this design, implementation plan, and progress handoff log.

The application should show the recommendation method, user inputs, product details, recommendation explanations, and a baseline-versus-proposed comparison. It should not require external credentials or paid services.

## 11. Constraints and implementation calls

- **Platform:** local Windows development environment.
- **Language:** Python.
- **Demo framework:** Streamlit, chosen for the short timeline and low frontend overhead.
- **Core ML:** pandas, NumPy, scikit-learn.
- **Charts:** Matplotlib or Seaborn, used only for a few explanatory plots.
- **Report:** Word-compatible output generated from a documented source; exact conversion method is a later implementation decision.
- **Dataset:** synthetic first, fixed seed, clearly labelled.
- **Scope:** one coherent demonstration is more important than many algorithms.
- **Explainability:** every recommendation should include a short reason.
- **Future changes:** keep data generation, features, models, evaluation, and UI in separate modules.

## 12. Success criteria

The project is ready for semester demonstration when:

1. A fresh environment can generate or load the dataset and run the app using documented commands.
2. The baseline and proposed recommender produce different, reproducible results.
3. A new product with no interaction history can appear for a suitable user based on content/value features.
4. The app displays recommendation reasons and does not expose internal implementation details as unexplained claims.
5. Classification and clustering outputs can be demonstrated or explained.
6. Evaluation results include at least one baseline comparison and cold-start-specific metric.
7. The report states the synthetic-data limitation and the boundary of the deep-learning experiment.
8. A new agent can read the progress log and continue without needing this conversation.

## 13. Open items deliberately left for implementation

- Exact synthetic dataset size, selected categories, and feature distributions.
- Exact folder layout for source code.
- Whether a small public dataset will supplement the synthetic data.
- Exact classification target and label-construction method.
- Exact report conversion tool available in the environment.
- Whether the optional neural-network comparison fits after the core demo is verified.

These are implementation details that can be settled without changing the project intent or the core demonstration.
