# Cold-Start Electronics Recommendation System Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a small, explainable Streamlit prototype that compares an established-product baseline with a content/value-based recommender for new electronics products and users.

**Architecture:** A reproducible synthetic-data generator creates products, users, and interactions. Focused Python modules then validate and transform the data, train the required classification and clustering demonstrations, calculate baseline and cold-start-aware recommendations, and evaluate them. A thin Streamlit application calls those modules and displays recommendations, explanations, and baseline-versus-proposed results.

**Tech Stack:** Python 3.11+; pandas; NumPy; scikit-learn; Streamlit; pytest; Matplotlib/Seaborn; python-docx or a documented Markdown-to-Word conversion path; python-pptx if available.

**Spec:** `docs/superpowers/specs/2026-11-10-cold-start-electronics-recommender-design.md`

## Global Constraints

- **Time budget:** 10 days, approximately 1 hour per day.
- **Project level:** Third-year college semester project.
- **Platform:** local Windows development environment.
- **Language:** Python.
- **Demo framework:** Streamlit, chosen for the short timeline and low frontend overhead.
- **Core ML:** pandas, NumPy, scikit-learn.
- **Dataset:** synthetic first, fixed seed, clearly labelled.
- **Scope:** one coherent demonstration is more important than many algorithms superficially.
- **Explainability:** every recommendation should include a short reason.
- **Deep learning:** optional enhancement, not a dependency for the main solution.
- **No external credentials or paid services.**
- **No Amazon scraping, private customer data, payment processing, authentication, or Amazon branding.**
- **Synthetic data must never be presented as real customer behavior.**
- **The implementation must keep data generation, features, models, evaluation, and UI in separate modules.**
- **The implementation must not begin until the student approves the design document.**

## Review Focus

- **Zero-history new item:** a product with no interaction rows must still be eligible for a suitable user through metadata; test in `tests/test_recommenders.py`.
- **Zero-history new user:** a user with preferences but no interactions must receive deterministic recommendations; test in `tests/test_recommenders.py`.
- **Missing or malformed input:** invalid category/budget or missing optional metadata must produce a clear validation error or safe fallback; test in `tests/test_features.py` and `tests/test_recommenders.py`.
- **Popularity bias:** the proposed method must not simply return the baseline list for every user; test with a controlled new-brand fixture in `tests/test_recommenders.py`.
- **Reproducibility:** generating data twice with the same seed must produce equivalent tables and metrics; test in `tests/test_data_generation.py` and `tests/test_evaluation.py`.

**Interfaces:**
- `popular_recommendations(products: pandas.DataFrame, interactions: pandas.DataFrame, top_k: int = 5) -> pandas.DataFrame`

Returned recommendation tables must contain product ID, product name, brand, category, score, rank, and reason. The baseline ranks by a documented popularity/rating combination and does not use unseen-item metadata to fabricate interaction history. The proposed method combines cosine content similarity, budget/price fit, warranty/offer/value signals, and a small exposure adjustment only for suitable new items. It must work for a new user with a preference dictionary and for a known user with interactions.
